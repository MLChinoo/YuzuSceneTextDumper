# 运行机理文档维护规范

## 必须更新的时机

适配新游戏、读取真实脚本/字节码或修改解释器处理时，发现新的 KAG / krkr / TJS 机制，必须在同一次工作中更新文档。新证据推翻旧结论、发现既有简化的反例、改变已记载的处理方式，也属于必须更新的情形。

先阅读 [文档入口](README.md) 和对应机制章节。通用概念放入 script-runtime.md；游戏专有行为放入对应游戏文档。新游戏需要较多记录时，新建 `docs/<游戏>-runtime.md`，并更新入口链接。不要将 DR 专有函数塞入通用引擎规则。

## 每条记录的内容

可以使用以下模板，也可以融入现有章节，但信息不能缺失：

```markdown
### 机制名称

- 适用范围：游戏、发行版本、基础/追加资源、解析器版本（已知时）。
- 确认程度：原版证据 / 数据观察 / 项目约定 / 待验证。
- 证据：仓库文件，或资源相对路径 + 函数/标签/字段名；官方说明链接。
- 输入示例：足以解释行为的最小脚本/JSON 片段。
- 运行机制：状态来源、计算过程、执行时机、作用域及副作用。
- 项目处理：对应 handler / config / parser；哪些部分已经实现。
- 差异与边界：简化、忽略行为、只适用于某些输入的前提。
- 待查项：未确认事项及下一步应查看的资源。
```

优先保存稳定的函数/标签定位，行号只作辅助。外部样本可能不在其他开发者机器上，因此写出资源相对路径，保存必要的小段证据；不要只写本机绝对路径或“见之前聊天”。反编译器还原出的临时变量名不应解释为原作者命名。

## 调查与判断方法

1. 找到样本中的读取和写入，以及调用时机，而不只是搜索某个变量名。
2. 检查选择记录、派生字段、系统持久状态和临时状态是否被混用。
3. 如果正文缺少赋值，追踪场景宏、插件回调、表驱动计算、追加资源和启动流程。
4. 对照当前 handler，区分“原版具备该行为”和“本项目实现了它”。
5. 确认失败时记录待验证及线索，不用猜测填补来源。统计结论写明日期及语料范围。
6. 修改代码时同步更新实现状态；只发现机制但未修改时写明当前差异。

用户规定代码修改后不运行测试；文档维护不会取消这一要求。没有运行验证时如实描述证据来自静态源码/样本观察。文档缺失不应成为无关代码改动、额外防御流程或自动提交的理由。

## 完成前核对

- 新机制已纳入对应章节并可从入口找到。
- 每个关键结论有证据定位及适用范围。
- 推测没有混入已确认行为；旧错误结论已更正，必要时说明更正依据。
- 代码状态与文档一致，未把其他 handler 描述成已同步升级。
- 未复制整份游戏资源、个人存档或大体积反编译产物进仓库。

本规范由仓库根级 [AGENTS.md](../AGENTS.md) 约束后续 agent 执行。
